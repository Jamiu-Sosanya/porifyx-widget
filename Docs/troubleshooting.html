1 Widget Not Showing on Website

You pasted the embed code into your website but the chat launcher button never appears — the page loads normally with no visible widget.

🚨

This was a known bug in versions prior to v1.0. The async loader queue was broken — the widget script loaded but the init call was silently dropped before the widget could render. This is fixed in the current release. If you are running an older copy, apply the patch below.

Root Cause

The embed snippet works by queuing the init call while widget.js loads in the background. When widget.js finally loaded, it replaced window.pfx with a new function — but in doing so it destroyed the .q queue property that held the pending init call. The check if (window.pfx.q) always evaluated to false, so the queue was never replayed and the widget never started.

Fix — Update widget.js

If you are applying this manually (older install), find the Public API block in public/widget.js and replace it with the corrected version below. The key change is capturing the queue before overwriting window.pfx.

// BEFORE (broken — .q is lost after reassignment) window.pfx = function (action, options) { if (action === 'init') init(options); ... }; if (window.pfx && window.pfx.q) { // always false — .q no longer exists ... } // AFTER (fixed — capture queue BEFORE overwriting window.pfx) const _queue = (window.pfx && window.pfx.q) ? window.pfx.q.slice() : []; window.pfx = function (action, options) { if (action === 'init') init(options); if (action === 'open' && config) { if (!isOpen) toggleChat(); } if (action === 'close' && config) { if (isOpen) toggleChat(); } }; // Replay any calls that were queued before the script loaded _queue.forEach(function (args) { window.pfx.apply(null, args); });

Also Check: Domain Restriction

If the widget does load on some domains but not others, the issue is likely the allowed-domains setting. When you enter a domain in the Security → Allowed Domains field, enter it without the protocol prefix:

Wrong ❌Correct ✅
https://example.comexample.com
http://www.mysite.com/www.mysite.com
https://shop.mystore.ioshop.mystore.io

Wildcards are supported — *.mysite.com will match any subdomain. After updating, click Save Widget and do a hard-refresh on the site where the widget is embedded.

After Applying the Fix

  1. 1

    Hard-refresh the page

    Browsers cache JavaScript aggressively. Press Ctrl + Shift + R (Windows / Linux) or Cmd + Shift + R (Mac) on the page where the widget is embedded to bypass the cache and load the new widget.js.

  2. 2

    Open the browser console

    Press F12 → Console tab. If the widget still does not appear, look for any red error messages. A 403 Domain not authorized error means the domain restriction setting needs updating (see above). A 404 means the widget.js URL is wrong in your embed code.

  3. 3

    Check the widget is active

    In the dashboard, go to Widgets → Your Widget → Settings and confirm the Widget Active toggle is turned on. Inactive widgets return a 404 from the API and will not render.

2 PDF Training Fails

You upload a PDF as a knowledge base source, click Retrain, and see one of these errors:

  • PDF file not found: training-sources/1/abc123.pdf
  • pdftotext is not installed on this server
  • SQLSTATE[22001]: String data, right truncated: 1406 Data too long for column 'content'

Error 1 — "PDF file not found"

This happens on Laravel 11 and newer. The local disk now stores files under storage/app/private/ instead of the old storage/app/ path. Older code used a hardcoded path that no longer exists.

💡

Already fixed in v1.0. The platform now uses Storage::disk('local') to resolve paths correctly. If you are on an older copy, update app/Services/TrainingService.php — the extractFromPdf() method must use Storage::disk('local')->exists() and Storage::disk('local')->path() instead of storage_path('app/').

Error 2 — "pdftotext is not installed"

The platform extracts text from PDFs using the pdftotext command-line utility, which is part of the poppler-utils package. This tool is not installed on all servers by default.

Install on Debian / Ubuntu (most common Linux hosting)

sudo apt-get update sudo apt-get install -y poppler-utils # Verify the install worked: pdftotext -v

Install on CentOS / RHEL / AlmaLinux

sudo yum install -y poppler-utils # or on newer versions: sudo dnf install -y poppler-utils

Install on cPanel / Shared Hosting

Most shared hosts do not give you root access to install system packages. Contact your hosting provider and ask them to install poppler-utils on the server. If they cannot, consider:

  • Upgrading to a VPS or cloud server (DigitalOcean, Vultr, Cloudways) where you have full root access
  • Converting your PDFs to plain text or FAQ format before uploading — these do not require pdftotext
  • Using a URL or website link source instead of PDF upload

Error 3 — "Data too long for column 'content'"

This error appeared in older versions when pdftotext was not installed. The platform fell back to reading the raw PDF binary file and tried to store the binary data in the database, which overflowed the column size. This fallback has been removed in v1.0 — you will now see the clear "pdftotext not installed" message instead of a database crash.

⚠️

If you still see the column overflow error after updating, you are running a version prior to v1.0. Apply the extractFromPdf() patch from app/Services/TrainingService.php — the dangerous raw-binary fallback must be removed entirely.

3 Training Times Out / Keeps Loading

You add a website URL as a knowledge base source (or click Retrain on an existing knowledge base) and the browser spins for 30–90 seconds before showing "This page is not working right now" or a gateway timeout error.

Why This Happens

Training a URL source involves several slow operations chained together:

  1. Fetching the URL over HTTP (up to 30 seconds per page)
  2. Chunking the extracted text into segments
  3. Calling the OpenAI embeddings API for each batch of chunks (multiple network round-trips)

For a sitemap source that crawls 50 pages, this can take 10–20 minutes. PHP and the web server both have execution time limits (typically 30–60 seconds) that kill the process long before it finishes, returning a blank error page.

💡

Already fixed in v1.0. The Retrain action now dispatches a background queue job instead of processing synchronously. Adding new sources already worked this way — Retrain has been updated to match. The HTTP response returns instantly; training happens in the background.

The Fix Requires a Queue Worker

Background jobs only work if something is consuming the job queue. The application uses a database queue (QUEUE_CONNECTION=database in .env). Jobs are written to the jobs table and stay there until a queue worker process picks them up and runs them.

🚨

If no queue worker is running, training will never complete — sources will stay stuck in "processing" or "pending" state forever. The queue worker is required for ALL training (both adding new sources and retraining).

See Section 4 — Queue Worker & Cron Job Setup for the full setup instructions.

4 Queue Worker & Cron Job Setup

The queue worker is a background process that runs continuously, picking up and executing jobs as they are added to the queue. It is required for:

  • Knowledge base training (URL, PDF, text, FAQ, sitemap sources)
  • Knowledge base retrain
  • Scheduled automations
  • Email notifications (if using queued mail)

Option A — VPS / Dedicated Server (Recommended)

On a server where you have SSH access, run the worker as a persistent daemon managed by Supervisor. Supervisor restarts the worker automatically if it crashes.

Step 1 — Install Supervisor

sudo apt-get install -y supervisor

Step 2 — Create a Supervisor config file

sudo nano /etc/supervisor/conf.d/aichat-worker.conf

Paste this content (replace /var/www/html with your actual project path and www-data with your web server user):

[program:aichat-worker] process_name=%(program_name)s_%(process_num)02d command=php /var/www/html/artisan queue:work database --sleep=3 --tries=3 --timeout=300 autostart=true autorestart=true user=www-data numprocs=1 redirect_stderr=true stdout_logfile=/var/log/aichat-worker.log stopwaitsecs=3600

Step 3 — Start the worker

sudo supervisorctl reread sudo supervisorctl update sudo supervisorctl start aichat-worker:* # Check it is running: sudo supervisorctl status

You should see aichat-worker:00 RUNNING. The worker will now survive server reboots automatically.

💡

After deploying code changes always restart the worker so it picks up any updated job classes: sudo supervisorctl restart aichat-worker:*

Option B — Shared Hosting (Cron-Based Worker)

Most shared hosts (cPanel, Plesk) do not allow long-running background processes. Instead, use a cron job that runs the queue worker every minute, processes all pending jobs, and then exits.

Step 1 — Log into cPanel

Go to your cPanel dashboard → Cron Jobs.

Step 2 — Add a new cron job

Set the frequency to Every Minute and enter this command (replace the path with your actual project root):

php /home/yourusername/public_html/artisan queue:work --stop-when-empty --timeout=300 --tries=3 >> /dev/null 2>&1
ℹ️

The --stop-when-empty flag tells the worker to exit as soon as the queue is empty. This prevents multiple cron instances from stacking up. A new cron fires every minute, picks up any new jobs, and exits cleanly.

Step 3 — Find your PHP path

On shared hosts, php may not be in the default path. Use the full path to your PHP 8.x binary. Common paths:

Host / SetupPHP Binary Path
cPanel default/usr/bin/php or /usr/local/bin/php
cPanel PHP 8.2 selector/usr/local/php82/bin/php
Plesk/opt/plesk/php/8.2/bin/php
Not sure?Run which php via SSH, or ask your host

Example with explicit PHP path:

/usr/local/php82/bin/php /home/yourusername/public_html/artisan queue:work --stop-when-empty --timeout=300 >> /dev/null 2>&1

Option C — One-off / Testing (SSH Only)

If you just want to test that training works without setting up Supervisor or cron, run the worker manually in your SSH session:

# Option A — one-shot: process everything in the queue then exit php artisan queue:work --stop-when-empty --timeout=300 # Option B — persistent (VPS / Supervisor): run continuously until stopped php artisan queue:work --timeout=300 --tries=3 # Option C — shared hosting cron (add to cPanel Cron Jobs, runs every minute): php /home/user/public_html/artisan queue:work --stop-when-empty --timeout=300 >> /dev/null 2>&1
⚠️

SSH testing only — as soon as you close your SSH session the worker stops. Use Supervisor (Option A above) or cron (Option B above) for production so the worker restarts automatically.

Verifying the Queue Is Working

After setting up the worker, test it end-to-end:

  1. 1

    Add a training source

    Go to Widgets → Your Widget → Knowledge Base → Add Source and add a short text or FAQ source. Click save. The status should show Pending immediately.

  2. 2

    Wait 1–2 minutes

    Refresh the knowledge base page. If the worker is running, the status will change from Pending → Processing → Completed. If it stays on Pending after 2 minutes, the worker is not running.

  3. 3

    Check for failed jobs (if status shows Failed)

    Run this via SSH to see any failed job error messages:

    php artisan queue:failed # To retry all failed jobs: php artisan queue:retry all

Also Add the Laravel Scheduler (Recommended)

The platform's scheduled tasks (daily stats cleanup, automation checks, etc.) also run through the queue. Add a second cron entry for the Laravel Scheduler so these tasks run automatically:

# Add this SEPARATE cron entry (runs once per minute): * * * * * php /home/yourusername/public_html/artisan schedule:run >> /dev/null 2>&1

On Supervisor / VPS setups, this cron entry should still be added — the scheduler is separate from the queue worker.

5 AI Chat Says "I'm Experiencing Technical Difficulties"

The widget loads and the visitor can type, but every AI reply comes back as:

I'm experiencing some technical difficulties. Please try again in a moment, or I can connect you with our team.

Root Causes (in order of likelihood)

1. OpenAI API Key Missing or Invalid

The AI can't call OpenAI without a valid key. Verify it is set correctly:

  1. 1

    Check the key is saved in Admin

    Go to Admin → Settings → AI Configuration. Paste your OpenAI API key and click the Test button next to it. You should see a green "Connection successful" message. If the test fails, the key is wrong — get a new one from platform.openai.com → API Keys.

  2. 2

    Confirm the key is written to .env

    After saving in Admin, open your .env file and check that OPENAI_API_KEY contains your key (not blank, not the literal text "your-key-here").

  3. 3

    Clear the config cache

    If you edited .env manually, the old cached config may still be loaded. Run via SSH:

    php artisan config:clear php artisan cache:clear

2. OpenAI Account Has No Credits

Even a valid API key fails if the account has run out of credits or the billing card is declined. Log into platform.openai.com → Billing to check your balance and add credits if needed.

3. AI Model Not Available to Your Account

Some models (like gpt-4o) require a paid OpenAI account with a certain usage history. If you are on a new account, try switching the widget to a more accessible model:

Go to Widgets → Your Widget → AI Settings and change the model to GPT-4o Mini (Fast) — this is the most accessible model across all account tiers.

4. Smart Suggestions Crashing the Response (Older Versions)

In versions prior to v1.0, if the smart-suggestions feature threw an internal error, it would also return "technical difficulties" even when the main AI reply was generated successfully. This masked the real response entirely.

💡

Fixed in v1.0. Smart suggestions are now wrapped in their own isolated try-catch. A suggestion failure logs a warning and returns an empty suggestion list — the AI response is always delivered regardless.

5. Duplicate Sentiment API Call Hitting Rate Limits (Older Versions)

In older versions, the sentiment-analysis API call was made twice for every visitor message — once in the HTTP handler and once inside the AI service. This doubled the OpenAI API calls per message, which could trigger rate-limit errors (HTTP 429) that then surfaced as "technical difficulties."

💡

Fixed in v1.0. The duplicate sentiment call inside AiChatService::generateResponse() has been removed. Each message now makes exactly one sentiment call.

How to Read the Actual Error

The real exception is always written to the Laravel log. SSH into your server and run:

# View the last 50 lines of the log (most recent errors at the bottom): tail -50 storage/logs/laravel.log # Or search specifically for AI errors: grep "AI API error" storage/logs/laravel.log | tail -20

The log entry will show the exact exception message from OpenAI (e.g., "Incorrect API key", "You exceeded your current quota", "The model does not exist"). That message tells you precisely which fix to apply.

ℹ️

You can also temporarily set APP_DEBUG=true in .env and run php artisan config:clear — the full exception will then appear in the browser for admin-origin requests, making diagnosis faster. Remember to set it back to false before sharing the site with visitors.

6 Automation "Division by Zero" Error

When creating or viewing an automation, you see a PHP error similar to:

DivisionByZeroError: Division by zero at app/Models/Automation.php line 42

Root Cause

The success_rate calculated attribute on the Automation model divides the success count by the trigger count. When trigger_count is zero (a brand-new automation that has never fired), this causes a division-by-zero crash.

The underlying cause was that MySQL returns integer columns as strings when there are no type casts configured. The guard if ($trigger_count === 0) used strict equality (===) — which always fails when comparing the integer 0 to the string "0", so the division always proceeded regardless of the value.

💡

Already fixed in v1.0. The trigger_count and success_count columns are now declared as 'integer' casts in the Automation model, so PHP always receives proper integers from the database. No manual action is required if you are running the latest version.

Manual Patch (Older Installs)

If you are on an older version, open app/Models/Automation.php and find the casts() method. Add these two lines inside the returned array:

// In App\Models\Automation — casts() method protected function casts(): array { return [ ... 'trigger_count' => 'integer', 'success_count' => 'integer', ... ]; }

If your problem is not listed here, enable debug mode (APP_DEBUG=true), capture the full error trace, and open a PoriFyx support ticket with your PHP version, hosting provider name, and the error message.
